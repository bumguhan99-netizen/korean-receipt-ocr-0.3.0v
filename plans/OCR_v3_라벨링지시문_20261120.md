# OCR v3 라벨링 지시문 (규칙 v1.0)

작성 2026-11-20 · 계획 문서 `OCR_v3_라벨링계획_20261120.md`

**사용법**
- 이 문서 전체를 작업자(사람 또는 AI 에이전트)에게 그대로 전달한다.
- 맡길 작업 묶음 번호(L1~L7)와 대상 영수증 목록을 함께 준다.
- 작업자는 이 문서에 없는 판단을 스스로 만들지 않는다. 판단이 필요하면 `needs_decision`으로 남긴다(§9).

---

## 1. 역할과 목표

너는 영수증 문자 인식(OCR) 학습 데이터의 라벨링 작업자다.

- 목표는 **이미지에 인쇄된 글자를 한 줄 단위로, 보이는 그대로** 정답으로 만드는 것이다.
- 이 정답은 한국어 인식 모델(PP-OCRv5)을 학습하고 평가하는 데 쓴다. 정답이 하나만 틀려도 모델은 그 오류를 배운다.
- 그래서 **확실하지 않은 줄은 추측해서 채우지 말고 제외한다.**

## 2. 절대 규칙

1. **원본을 수정하거나 지우지 않는다.**
   - 원본: `ocr_v3/data/originals/`, `ocr_v3/data/korie/`, `ocr_v2_retrain/datasets/raw/`
   - 결과는 지정된 새 폴더에만 쓴다. 같은 이름의 파일이 있으면 덮어쓰지 말고 멈춘 뒤 보고한다.
2. **모든 줄은 이미지를 직접 보고 확인한다.**
   - 초안(OCR 결과, 기존 정답, CSV 힌트)을 이미지 확인 없이 그대로 옮기지 않는다.
   - AI 에이전트가 이미지를 볼 수 없는 상황이면 작업을 멈추고 보고한다.
3. **맞춤법을 고치지 않고, 문맥으로 추측하지 않는다.**
   - 영수증에 오타가 인쇄되어 있으면 오타 그대로 쓴다.
   - 흐려서 안 보이는 글자를 상품명이나 상식으로 채우지 않는다.
4. **평가 데이터는 블라인드로 라벨링한다.** `split`이 `val`, `test`, `holdout`인 줄에는 인식 모델 예측(v1·v2·v3·pretrained)을 보지도 쓰지도 않는다.
5. **영수증 이미지와 문자열을 외부 서비스(웹 OCR, LLM API, 번역기 등)로 보내지 않는다.** 카드번호 일부, 상호, 주소 같은 개인정보가 들어 있다.
6. **분할(`split`)을 바꾸지 않는다.** 분할은 주어진 분할 파일에서만 가져온다.
7. 한 영수증의 모든 줄은 한 작업자가 한 번에 끝낸다. 중간에 넘기면 넘긴 지점을 기록한다.

## 3. 입력과 출력

| 구분 | 경로 | 내용 |
|---|---|---|
| 분할 파일 | `ocr_v3/data/labels_v3/splits.json` | 영수증 ID → 분할. 읽기만 한다 |
| phone 원본·기존 라벨 | `ocr_v2_retrain/datasets/raw/receipt_labeled/` | `aligned_images/`, `labels/rXXX.json`, `recognition_verified.txt`, `excluded.csv` |
| 52장 | `ocr_v2_retrain/datasets/raw/{images,labels}` | Windows OCR 자동 초안(미검수) |
| KORIE | `ocr_v3/data/korie/` | `text_crops/*.zip`(공식 crop + 정답), `receipts/`(원본 + YOLO 박스), `receipt_fields/*.csv`(IE) |
| det 박스 | `ocr_v3/data/labels_v3/det_cache/` | 배포와 같은 검출 결과(묶음 L4·L5·L1용). 만든 사람이 해시를 기록한다 |
| **출력** | `ocr_v3/data/labels_v3/` | `lines.jsonl`(줄 레코드), `crops/`, `changes.csv`, `reports/<묶음>_<날짜>.md` |

줄 레코드의 키는 계획 문서 §3-1을 따른다. 최소한 다음 키는 반드시 채운다: `line_id`, `source`, `receipt_id`, `split`, `box`, `text`, `status`, `exclude_code`, `flags`, `draft_source`, `annotator`, `reviewed_at`, `rules_version: "v1.0"`.

## 4. 박스 규칙

1. **한 박스 = 한 줄의 연속된 글자 묶음**이다.
   - 위아래로 두 줄 이상이 들어가면 나눈다.
   - 같은 줄이라도 글자 사이 빈칸이 **숫자 두 글자 폭 이상**이면 다른 열로 보고 박스를 나눈다(예: 품목명 / 수량 / 금액).
2. **det 박스가 주어진 묶음(L1·L4·L5)은 det 박스를 기본으로 한다.** 다음 경우에만 고친다.
   - 두 줄 이상을 담고 있다 → 줄별로 나눈다.
   - 글자를 자르고 있다(획 일부가 박스 밖) → 넓힌다.
   - 인쇄 글자가 아닌 것(바코드, 로고, 배경)을 담고 있다 → 제외(E07).
   - det가 한 줄을 여러 조각으로 나눈 것은 **그대로 둔다.** 배포에서도 그렇게 잘리기 때문이다. 단, 한 글자가 반으로 잘렸으면 넓힌다.
3. 여백은 글자 높이의 약 10~20%를 둔다. 위아래 획(ㅎ, g, y)과 위첨자 기호가 잘리지 않게 한다.
4. 기울어진 줄은 기울기를 따라 네 점(quad)으로 잡는다. 점 순서는 왼쪽 위부터 시계 방향이다.
5. 인접 줄의 획이 박스 안에 조금 들어오는 것은 박스를 조정해 최대한 뺀다. 뺄 수 없고, 들어온 획이 글자로 읽힐 정도면 제외(E01)한다.

## 5. 전사 규칙

### 5-1. 문자

| 대상 | 규칙 | 예 |
|---|---|---|
| 한글 | 완성형 음절로 입력한다. 저장 전 NFC 정규화를 한다. | `카페라떼` |
| 단독 자음·모음 | 호환 자모(U+3131~U+318E)로 입력한다. 키보드로 입력한 값이 그대로 이것이다. | `ㄴ`, `ㅇ` |
| 영문·숫자·기호 | **반각**(일반 키보드 문자)으로 입력한다. 전각 문자(`＆`, `１`)를 쓰지 않는다. | `A`, `1`, `&` |
| 대소문자 | 보이는 대로 입력한다. | `Coffee`, `COFFEE` |
| 숫자 구분 기호 | 쉼표·마침표·하이픈·콜론·슬래시를 보이는 대로 입력한다. 빠뜨리거나 더하지 않는다. | `12,500`, `2024.03.15`, `02-123-4567` |
| 통화 표기 | 보이는 대로 입력한다. `₩`는 `W`로 바꾸지 않는다(OOV 표시). | `₩12,500`, `12,500원` |
| 괄호 | 종류를 구분해 입력한다. | `( )`, `[ ]`, `「 」`, `〔 〕` |
| 한자, 특수 기호(♥ ★ ◆ ☎ 등) | 보이는 문자 그대로 입력하고 `oov` 플래그를 단다. 비슷한 글자로 바꾸지 않는다. | `☎02-...` |
| 마스킹 `*` | 개수를 정확히 센다. 개수가 확실하지 않으면 제외(E06). | `1234-****-****-5678` |
| 취소선, 반전 인쇄(흰 글씨) | 읽을 수 있으면 입력하고 메모를 남긴다. 못 읽으면 E03. | |

- 위 예시 문자열은 설명을 위해 지어낸 것이다.

### 5-2. 하지 않는 것

- 맞춤법·띄어쓰기 교정
- 축약 풀기(`아메`를 `아메리카노`로 바꾸지 않음)
- 단위 정규화(`1,000원`을 `1000`으로 바꾸지 않음)
- NFKC 정규화
- 문맥 없는 문자 치환(`₩→W`, `＆→&` 같은 자동 치환)

### 5-3. 공백 규칙 (가장 자주 틀리는 부분)

1. **기준 단위:** 그 줄의 숫자 한 글자 폭을 1칸으로 본다.
2. 두 글자 사이 빈 간격이 **0.5칸 이상이면 공백 1개**를 넣는다. 0.5칸 미만이면 붙여 쓴다.
3. 간격이 **2칸 이상이면 열 구분**으로 보고 박스를 나눈다(§4-1). 한 박스 안에서 공백은 항상 1개다. 연속 공백, 앞뒤 공백은 넣지 않는다.
4. **날짜·시간·전화번호도 같은 규칙**을 적용한다. 관례로 판단하지 않고 이미지 간격으로만 판단한다.
   - 점 뒤 간격이 0.5칸 이상: `2024. 03. 15`
   - 간격이 없음: `2024.03.15`
5. 0.5칸 근처라 판단이 어려우면 붙여 쓰고 `uncertain_space` 플래그를 단다.
6. **새로 입력하는 줄**은 처음부터 이 규칙을 따른다.
7. **기존 정답이 있는 줄**(KORIE 공식 정답, phone verified 정답)은 다르게 처리한다.
   - 공백만 이 규칙과 다르면 **고치지 않고** `space_mismatch` 플래그만 단다.
   - 일괄 수정 여부는 L3 감사 결과를 보고 사용자가 정한다. 결정이 나면 규칙 v1.1로 한꺼번에 반영한다(원래 값은 `original_text`, 사유 `space_rule`).
   - 공백 외의 글자가 다르면 §8 각 묶음의 절차대로 고친다.

### 5-4. 길이

- 길이 제한은 없다. 긴 줄도 전부 입력한다.
- 24자 이상이면 `long` 플래그를 단다. 학습 제외 여부는 라벨링 단계에서 정하지 않는다.

## 6. 제외 규칙과 사유 코드

**먼저 박스를 고쳐서 해결할 수 있는지 본다.** 박스 수정으로 해결되지 않을 때만 제외한다. 제외 사유는 아래 코드 중 하나만 고르고, 자유 서술은 `note`에만 쓴다.

| 코드 | 사유 | 판정 기준 |
|---|---|---|
| E01 | 인접 줄 혼입 | 박스를 조정해도 다른 줄의 글자가 읽힐 만큼 들어온다 |
| E02 | 글자 잘림 | 이미지 경계, 접힘, 찢김으로 글자 일부가 사라졌다. 박스를 넓혀도 복구되지 않는다 |
| E03 | 판독 불가 | 흐림, 번짐, 바램, 저해상도로 한 글자라도 확정할 수 없다 |
| E04 | 손글씨·수기 수정 | 인쇄 글자 위에 손글씨가 있거나, 손글씨만 있다 |
| E05 | 겹친 인쇄·도장 | 다른 인쇄나 도장이 글자를 가린다 |
| E06 | 마스킹 개수 불명 | `*` 같은 가림 문자의 개수를 확정할 수 없다 |
| E07 | 문자 아님 | 바코드, QR, 로고 그림, 배경 무늬, 구분선만 있는 줄(`-----`, `=====`, `*****`) |
| E08 | 세로쓰기·특수 배치 | 세로 글자, 원형 배치 등 한 줄로 쓸 수 없다 |
| E09 | 기타 | 위에 없는 사유. `note` 필수 |

- 한 줄에서 **한 글자라도 확정할 수 없으면 줄 전체를 제외**한다. 그 글자를 `?`나 빈칸으로 남긴 정답을 만들지 않는다.

## 7. 상태와 플래그

| 상태 | 의미 |
|---|---|
| `verified` | 이미지와 한 글자씩 대조해 확정했다 |
| `excluded` | 제외. `exclude_code` 필수 |
| `needs_decision` | 규칙으로 판단할 수 없다. `note`에 질문을 적는다(§9) |

| 플래그 | 언제 |
|---|---|
| `oov` | 한자, 특수 기호 등 문자 사전에 없을 수 있는 문자가 있다(목록은 자동 검사가 다시 확인한다) |
| `long` | 24자 이상 |
| `masked` | `*` 등 가림 문자가 있다 |
| `uncertain_space` | 공백 판단이 경계에 있었다 |
| `space_mismatch` | 기존 정답의 공백이 §5-3 판정과 다르다(아직 고치지 않음) |
| `text_changed` | 기존 정답을 바꿨다(`original_text` 필수) |
| `box_changed` | 주어진 박스(det, 기존)를 고쳤다 |

## 8. 작업 묶음별 절차

### L1. 52장 holdout 검수

1. 분할이 `holdout`인 영수증 24장만 작업한다. 304장과 같은 28장은 작업하지 않는다.
2. det 박스를 기준으로 §4에 따라 박스를 정리한다.
3. 초안은 Windows OCR 결과만 쓸 수 있다. 인식 모델 예측은 쓰지 않는다. 초안 없이 직접 입력해도 된다.
4. 인쇄된 줄은 하나도 빠뜨리지 않는다. 박스가 없는 인쇄 줄은 새 박스를 그린다.

### L2. KORIE 여러 줄 crop 분할

1. 대상은 목록으로 받은 crop(가로/세로 비 < 1)이다.
2. crop 안에 줄마다 박스를 그린다.
3. 기존 정답 문자열을 줄 순서(위 → 아래)로 나눈다.
   - 나눌 때 원래 줄 사이에 있던 공백 1개는 빼고, 글자는 바꾸지 않는다.
   - 기존 정답과 이미지가 다르면 이미지를 따르고 `text_changed`를 단다.
4. 새 ID는 `<원래 crop ID>#l1`, `#l2` …로 하고 `parent_id`에 원래 ID를 쓴다.
5. val/test crop도 같은 방법으로 처리한다. 모델 예측은 보지 않는다.

### L3. 형식 필드 공백 감사

1. 받은 목록(날짜·시간·전화 crop)마다 §5-3으로 공백을 판정한다.
2. 판정 결과를 `space_judgement`(공백있음/공백없음/경계)로 기록한다. 기존 정답이 판정과 같은지(`label_matches_image`)도 함께 기록한다.
3. 감사 단계에서는 정답을 고치지 않는다. 수정 여부는 감사 보고를 본 뒤 사용자가 정한다(계획 §7-2).

### L4. phone det 재박스

1. 영수증마다 det 박스와 기존 verified 줄의 매칭표를 받는다(1:1, 분할, 병합, 신규, 미매칭).
2. **1:1 매칭:** 기존 정답을 이미지와 대조한다. 같으면 `verified`, 다르면 고치고 `text_changed`를 단다.
3. **분할·병합:** §4 박스 규칙으로 박스를 정리하고 정답을 새로 입력한다. 기존 정답은 참고만 한다.
4. **신규(기존 정답 없음):** 인쇄 글자면 새로 입력하고, 아니면 E07.
5. **기존 제외 줄:** 새 박스에서 다시 판단한다. 박스 문제로 제외됐던 줄은 대부분 복구 대상이다.
6. 초안 사용 범위: `train` 줄은 v1 최종 모델 예측을 초안으로 써도 된다. `val`/`test` 줄은 기존 verified 정답만 쓴다.

### L5. KORIE 품목명 줄

1. det 박스 중 품목 영역(품목명·수량·단가·금액이 있는 표)의 박스만 작업한다.
2. IE CSV `Item_Name`은 같은 영수증의 품목 순서를 짐작하는 힌트로만 쓴다. 쉼표로 이어진 값을 정답에 그대로 붙여 넣지 않는다.
3. 줄마다 이미지를 보고 입력한다.
4. `val`/`test` 영수증은 같은 규칙으로 하되 모델 예측을 보지 않는다.

### L6. 오류 감사

1. 받은 표본 목록의 줄을 이미지와 한 글자씩 대조한다.
2. 줄마다 결과를 하나 고른다: `correct`, `error_space`, `error_char`, `error_missing`, `error_extra`, `error_box`, `unreadable`.
3. 틀린 줄은 고친 정답을 함께 적는다. 실제 반영은 감사 보고 승인 뒤 한다.
4. `val`/`test`/`holdout` 표본에는 모델 예측이 들어 있지 않다. 예측을 따로 찾아보지 않는다.

### L7. 전체 커버리지 박스

1. 영수증의 **인쇄된 모든 줄**에 박스를 단다. 상단 로고 글자, 하단 안내 문구, 작은 글씨를 포함한다.
2. 전사 규칙과 제외 규칙은 위와 같다. 제외한 줄도 박스는 남긴다(검출 평가에 쓴다).

---

## 9. 판단이 어려울 때

1. 이 문서로 판단할 수 없으면 `status: needs_decision`으로 두고 `note`에 질문을 적는다.
   - 예: "점 뒤 간격이 약 0.5칸으로 경계. 붙여 쓸지?"
   - 예: "상호에 한자 1자가 있는데 사전에 없음. 그대로 둘지?"
2. 같은 종류의 질문이 3건 이상 모이면 묶음 보고에 따로 모은다.
3. 사용자 결정이 나면 규칙을 v1.1로 올려 반영한다. 이미 처리한 줄 중 영향 받는 줄 목록도 만든다.
4. 결정을 기다리는 동안 다른 줄 작업은 계속한다.

## 10. 제출 전 자체 검사

- [ ] 모든 줄에 `status`가 있고, `excluded`에는 코드가, `needs_decision`에는 메모가 있다.
- [ ] `text`에 앞뒤 공백, 연속 공백, 탭, 줄바꿈이 없다.
- [ ] `text`가 NFC 정규화 후에도 바뀌지 않는다.
- [ ] 전각 영문·숫자가 없다.
- [ ] 24자 이상인 줄에 `long`이 있다. 한자·특수 기호가 있는 줄에 `oov`가 있다.
- [ ] 고친 줄에 `original_text`, `text_changed`가 있고 `changes.csv`에 기록됐다.
- [ ] 기존 정답의 공백만 다른 줄은 고치지 않고 `space_mismatch`만 달았다.
- [ ] 박스가 이미지 안에 있고, crop 파일이 비어 있지 않다.
- [ ] `split`이 분할 파일과 같다.
- [ ] val/test/holdout 줄에 모델 예측 초안을 쓰지 않았다(`draft_source` 확인).
- [ ] 원본 폴더의 파일을 하나도 바꾸지 않았다.

## 11. 묶음 보고 형식

파일 `reports/<묶음>_<YYYYMMDD>_<작업자>.md`에 다음을 적는다.

| 항목 | 값 |
|---|---|
| 묶음·대상 | 예: L4, phone r001~r020 |
| 규칙 버전 | v1.0 |
| 처리 줄 수 | verified / excluded / needs_decision |
| 사유 코드별 제외 수 | E01 … E09 |
| 바뀐 줄 수 | 공백만 / 글자 / 박스 |
| 새로 만든 줄 수 | 분할 / 신규 |
| 소요 시간 | 시작·종료 시각 |
| 미결정 질문 목록 | `line_id`와 질문 |
| 자체 검사 | §10 항목 통과 여부 |
